# routes_A_D — A_D 地圖的**去程單程**路線

由 Jetson 上的 `~/maps/A_D.stcm`（278 MB，1441 keyframes，總時長 51.5 分）用
`extract_oneway.py` 抽出。**只抽去程**——這張圖的回程是壞的（見下方診斷）。

## 檔案
- `plan_A_D.csv` — **去程 A→D，432.7 m，752 waypoint**，可直接餵 `ros_move_follow_route.py`
- `pass_00.csv` / `index.yaml` / `stations.yaml` — 同 extract_route.py 格式，之後要在路上加 B 站點時給 `route_graph.py` 用
- `preview.png` — 擷取段（藍）疊在整張圖軌跡（灰）上
- `sim_A_D.png` — 離線模擬軌跡
- `diagnosis.png` — 去程 / 回程正常段 / 回程崩潰段的三色圖

品質：相鄰 waypoint 最大間距 **1.25 m**、**零跳點**（>1.5 m 的 0 處）；
離線模擬 @0.6 m/s 橫向誤差中位 **0.15 m**、最大 0.62 m（發生在里程 379 m 的
`(284,89)` 急轉彎，pure pursuit 切彎；D 前最後轉彎只有 0.47 m）。

## 切點怎麼定的（KF 136–3782）
### 終點：**第二次擺動**的位置 `(329.05, 112.77)`
車到終點區之後**擺動了兩次，中間有個轉彎**：

| | KF | 位置 | 停留 |
|---|---|---|---|
| 抵達 → 擺動 1 | 3632–3743 | (330.53, 109.85) | 57 s |
| 轉 96° 前進 2.9 m | 3763–**3782** | 航向 21°→117° | — |
| **擺動 2 = D** | 3798–3923 | **(329.05, 112.77)** | 66 s |
| 之後 | 3924– | 退回 (330.3,109.7) 再往回開 | |

兩處只差 3.0 m，所以終點取 **KF 3782**（開進第二處的最後一個前進 keyframe）。

`--half first` 的自動折返偵測在這張圖上會切在 **KF 4158**，那已經是**離開 D 往回開
8 m 的位置** —— `split_passes` 的迴轉判定被上面那些 <0.2 m 的擺動濾掉了
（`REV_MIN_MOVE=1.0`），所以偵不到真正的終點。必須手動指定 KF 範圍。

### 三個清理步驟（缺一不可）
- **`--exclude 3632:3743`** 挖掉擺動 1。它在 0.3 m 的範圍內來回卻累積 1.8 m 里程，
  pure pursuit 的前視點 `cum[i_near]+LOOKAHEAD` 會落進那一團裡，實際前視距離塌到
  **0.13 m**（`Ld` 下限），車會在 D 前原地亂轉。挖掉後接縫落差只有 0.25 m。
- **`--min-step 0.25`** 抽稀掉其他停等時累積的原地點（共 327 個）。不抽稀的話全線有
  **62 個** waypoint 的實際前視距離 < 0.4 m，最小 **0.005 m**（等於沒有前視），
  而且不只在 D —— 起點附近 `(-8.3,-3.5)` 的原地轉彎也有。清完只剩路線最後一個
  waypoint（它的前視目標就是終點本身，任何路線都這樣，無害）。
- **`--trim-start 1.5`** 修掉 A 點的起步擺動（車在 A 的 ±0.3 m 內晃了 79 s）。
  不修的話 `field_test.sh` 的 preflight 會拿那幾個擠在一起的 waypoint 算路線方向，
  得到的是雜訊。修完後起點 `(-0.5,-0.3)`（離 A 0.6 m），`wp[0]→wp[3]` 位移 0.63 m、
  航向 −158°，穩定。

## 路線形狀（從航向算出來）
| 里程 | 內容 |
|---|---|
| 0–48 m | A 附近的起始彎繞 |
| 48–344 m | **292 m 筆直開闊走廊**，航向恆定 21°，離擬合直線 RMS 0.24 m |
| 359 m | `(292,70)` 處 **90.8° 左轉**，離開走廊 |
| 379 m | `(284,89)` 處右轉朝東北（模擬中橫向誤差最大的地方，0.62 m） |
| 379–430 m | 建築區走到 `(330.5,109.8)`，含最後那個彎 |

這條 292 m 走廊就是 CLAUDE.md 說的「開闊、自相似、純視覺 SLAM 難定位」那一段。

## 回程為什麼壞掉（診斷結論）
| 階段 | 資料 |
|---|---|
| 去程 A→D | 455.6 m / 36.5 min / 均速 0.21 m/s，keyframe 密度均勻 2.5 KF/m，**健康** |
| 回程 D→(292,70) | 89 m / 7 min，離去程路徑僅 **0.07–0.74 m**，兩方向對齊良好，**健康** |
| 回程 (292,70) 之後 | **崩潰**：keyframe id 消耗從 3.4/KF 暴增到 22.8 → 77，速度掉到 0.00–0.06 m/s，8 分鐘只挪了 8 m，最後 163 s 完全不動，session 結束 |

崩潰點就是那個 **90° 轉角**，也就是車從建築區**要轉進 292 m 開闊走廊的入口**。
建築區反向看仍有足夠特徵（所以前 89 m 沒事），一轉進走廊，畫面變成磚地＋草地＋遠樹，
反方向又匹配不到去程的 keyframe，追蹤立刻失效且再也沒恢復。

副作用：崩潰後那 51 個亂跑的 keyframe 會被 `extract_route.py` 切成兩條 6 m 的碎 pass
（中間還夾一個 4.3 m 跳點），它們的座標就疊在去程路徑上、落在 `snap_radius` 內
→ `route_graph.py` 的 Dijkstra 有機會跳上去，plan 就長出跳點。**這就是「回程亂掉」的機制。**

## 已接上的入口

  `$PLANS/plan_*.csv` **自動產生**（換圖不必改腳本），且啟動時會擋下「路線與地圖

- `robot_menu.sh` 選單 4 → `autopilot_test.sh`：路線清單自動掃到 `routes_A_D/plan_A_D.csv`，
  選了之後**自動配對** `index.yaml` 裡記的來源地圖 `A_D.stcm`，不用再自己選圖。

## 重新產生
```bash
cd ~/Go_by_my_self/Detect/new_detect/route
python3 extract_oneway.py ~/maps/A_D.stcm --report                       # 診斷
python3 extract_oneway.py ~/maps/A_D.stcm --out routes_A_D --png \
        --kf 0:3782 --exclude 3632:3743 --trim-start 1.5 --min-step 0.25  # 抽去程
python3 ros_move_follow_route.py --plan routes_A_D/plan_A_D.csv --sim --render routes_A_D/sim_A_D.png
```
註：`.stcm` 解析用純 Python msgpack 約 3.5 分鐘。加 `--dump-kf ~/A_D_kf.csv` 可在同一趟
把原始 keyframe 存成小 CSV；之後 `extract_oneway.py ~/A_D_kf.csv ...` 直接吃那個 CSV，
秒讀，調切點不必再解析大檔。

## 回程要怎麼辦
不要在這張圖上補回程。**另外建一張 D→A 的單程圖**（`~/maps/D_A.stcm` → `routes_D_A/`）：
崩潰的根因是「反方向匹配既有圖層」+「低紋理走廊」兩者疊加，新 session 沒有既有圖層
可衝突，那個轉角有機會過得去 —— 但要現場驗證。建圖時在 `(292,70)` 那個轉角**停下來、
慢慢轉**，並維持去程那種 ~0.2 m/s 的速度。
